# Rewrite Assistant v3.0.1 — UX/UI and Product Audit — 2026-09-17

## Scope

This audit covers the current Rewrite Assistant React extension on Marinara Engine 2.4.6, with emphasis on the selection popup, result flow, Settings information architecture, keyboard accessibility, visual density, performance-sensitive interaction, provider UX, and release safety. The visual baseline entering this pass is commit `d5f464314d877230a1dc93e35536bd474cd4fa8b` (`feat: rebalance popup information architecture`).

## External benchmark set

The goal is not to imitate another product's appearance. The benchmark is used to extract interaction principles that are repeatedly present in high-quality productivity software and mature design systems.

- Linear — "Welcome to the new Linear" and "How we redesigned the Linear UI": hierarchy, balance, density, reduced visual noise, clearer headers/panels. https://linear.app/changelog/2024-03-20-new-linear-ui and https://linear.app/now/how-we-redesigned-the-linear-ui
- Linear — contextual/new command menu: commands are contextual, grouped, searchable when scale requires it, and invoked close to the UI element that triggered them. https://linear.app/changelog/2019-10-07-contextual-command-menu and https://linear.app/changelog/2019-12-18-new-command-menu
- Apple HIG — Context menus / Toolbars: prioritize relevant and frequent actions, avoid overcrowding, use clear grouping and recognizable actions. https://developer.apple.com/design/human-interface-guidelines/context-menus and https://developer.apple.com/design/human-interface-guidelines/toolbars
- Radix Primitives — Accessibility / Popover / Toolbar / Dialog: keyboard navigation, focus management, Escape dismissal, roving focus for grouped controls, collision-aware overlays. https://www.radix-ui.com/primitives/docs/overview/accessibility , https://www.radix-ui.com/primitives/docs/components/popover , https://www.radix-ui.com/primitives/docs/components/toolbar , https://www.radix-ui.com/primitives/docs/components/dialog
- Figma — Design systems foundations: consistency in accessibility, color, typography, iconography and dimensions; semantic color use and accessibility should be systemic rather than layered on at the end. https://www.figma.com/blog/design-systems-102-how-to-build-your-design-system/ and https://www.figma.com/blog/figma-pattern-library/

## Product-level conclusions

### 1. Popup hierarchy

The original screenshot had four structural problems: the product header visually merged into the command region; the Context/Sources/Adjust area competed as three equally heavy boxes; unused vertical space appeared inside the Context and Adjust columns; and the footer distributed actions across a rigid grid that created dead zones.

The current 620px popup corrects those issues by using a dedicated header divider, a compact style heading, a full-width Context summary row, an 8/4 Sources/Adjust working split, and a flex footer. This is directionally consistent with Linear's reduction of panel noise and clearer navigation/header hierarchy.

### 2. Density

The popup should remain dense because it is a contextual productivity surface, but density must come from removing redundant hierarchy rather than shrinking text and hit targets until the UI feels compressed. The current pass therefore keeps the 30px rewrite-style controls and 32px footer actions while removing redundant kicker text and large internal gaps.

No blur/glassmorphism layer is recommended. It would increase paint cost and reduce text contrast without improving task clarity. The current low-paint opaque surfaces are appropriate for an extension that overlays an existing chat application.

### 3. Command organization

With the current default set of roughly 13 rewrite styles, direct visibility remains faster than introducing a search field. Linear's searchable command-menu pattern becomes more valuable when the command inventory grows substantially. A useful future threshold is approximately 20+ visible styles or evidence from users that scanning has become slower than typing.

The popup should continue to put rewrite styles first, then contextual controls, then lower-frequency utility actions. This matches the principle of presenting commands most relevant to the current selection first.

### 4. Context controls

Context is not one homogeneous control group. The UI now separates:

- target/estimated prompt summary,
- source inclusion,
- one-shot per-rewrite exclusions,
- output modifiers.

That information architecture is more legible than three equal columns because it reflects task order: understand what will be rewritten, decide what context participates, then adjust output length/history.

### 5. Footer actions

Undo and Redo are compact icon actions because their meaning is conventional and they are state-dependent. Custom Prompt receives the largest action area because it is the main escape hatch from presets. Settings remains visible but secondary. This follows the toolbar principle of prioritizing frequent actions while avoiding equal visual weight for every command.

### 6. Keyboard and assistive-technology gap found in this audit

The visual redesign alone was not sufficient. The style grid still exposed every preset as an independent Tab stop, custom tooltips were mouse-only, and the non-modal popup had no standard Escape dismissal path when focus remained on the page.

This pass closes those interaction gaps:

- style presets use roving keyboard focus with Left/Right/Up/Down plus Home/End,
- the navigation reads the computed CSS column count so responsive layouts remain correct,
- preset and Auto Profile explanations are available on keyboard focus and through `aria-description`,
- Context help is available on focus, not only hover,
- Escape dismisses the selection popup while explicitly yielding to any active dialog.

These changes are directly aligned with the interaction expectations documented by Radix and WAI-ARIA-style component behavior, without replacing Rewrite Assistant's existing React architecture.

## Whole-extension audit

### Architecture and isolation — strong

- React/Zustand runtime remains isolated in a closed Shadow DOM.
- The current popup, Settings, and Result visual systems use separate namespaces instead of relying on one global selector family.
- Network access is centralized through the Marinara host adapter.
- Private extension storage remains authoritative on modern Marinara hosts, with guarded one-time migration from page storage.
- Runtime import cycles and high-risk JavaScript patterns are blocked by dependency-free source gates.

### Provider and LAN behavior — strong with environment-dependent residuals

- Marinara inference resolves the current chat connection before fallback.
- Empty raw-generation output receives one explicit reasoning-disabled retry.
- Direct LAN URLs receive longer timeouts and normalized diagnostics for browser/network failures.
- LAN Ollama `Failed to fetch` can still depend on listen address, firewall and CORS/PNA configuration outside the extension. That class of failure cannot be fully proven by repository tests alone.

### Result/Preview recovery — strong

- Generated text remains recoverable as raw selectable text.
- Copy and Save `.txt` paths exist independently of destructive apply.
- Apply state suppresses duplicate writes.
- Diff and long-output behavior have bounded fallback paths.

### Data integrity — strong with known Engine limitation

- Selection identity and server metadata are revalidated before destructive writes.
- Message writes fail closed on content drift.
- Marinara 2.4.6 still does not provide a true conditional-update/CAS primitive for message PATCH, so a very small GET→PATCH TOCTOU window remains a host API limitation rather than an extension UI defect.

### Settings — structurally strong

- The Settings window already uses a sidebar/workspace information architecture instead of a large flat form.
- API, Context, Profiles, UI and Data are separated into distinct task areas.
- Current-chat Marinara connection behavior is represented in Settings without adding a duplicate model selector.

The next Settings-level improvement should be evidence-driven rather than another visual rewrite: observe which sections users enter most often, then consider contextual shortcuts from the popup for those specific settings only.

## Visual system guidance retained for subsequent work

- Opaque near-black surfaces with subtle elevation, not blur-heavy glass.
- Amber is an accent, not a fill color for every control.
- One dominant text hierarchy per region; avoid repeated all-caps labels unless they function as real section markers.
- Use spacing and thin dividers before adding more containers.
- Keep permanent chrome visually quieter than task content.
- Do not encode state by color alone; preserve text, icon, switch position or helper copy.
- Responsive behavior must preserve minimum readable cell widths and avoid horizontal overflow.

## Validation requirements after this pass

Repository CI must remain green for source, regression, failure-mode, property/fuzz, manifest, UX lifecycle, popup architecture, popup readability/focus, popup interaction, Settings architecture, LAN/result UI, dependency audit, ESLint, Vite production build, installable JSON validation, Engine 2.4.4 compatibility and Engine 2.4.6 compatibility.

Manual visual acceptance is still required at 100%, 125% and 150% browser zoom because static CSS gates cannot judge optical balance, host-font rasterization, or how the overlay feels on the real chat canvas. The most important screenshots are: default 13-style popup, long profile names, compact mode, narrow viewport, Free Mode on, Auto Profile present, and a multi-message selection.
